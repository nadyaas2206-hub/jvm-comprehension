# Понимание JVM

## Немного теории, чтобы дальше было понятно

Когда мы запускаем Java-программу, работает не сама программа, а **JVM (Java Virtual Machine)** — виртуальная машина, которая выполняет байт-код. Она берёт на себя управление памятью, загрузку классов, сборку мусора и многое другое.

### ClassLoader'ы

Классы в JVM не появляются «сами по себе», их загружают специальные штуки, которые называются **ClassLoader'ами**. Их три, и они работают по цепочке:

1. **Bootstrap ClassLoader** — самый главный, загружает базовые классы Java (`Object`, `String`, `System`, `Integer` и т.д.). Он написан не на Java, а на нативном коде.
2. **Platform ClassLoader** — загружает классы расширений JDK.
3. **Application ClassLoader** — загружает классы нашего приложения (то есть `JvmComprehension`).

Работает это так: Application просит Platform, Platform просит Bootstrap. Если Bootstrap не находит класс, идём обратно вниз по цепочке. Это называется **делегирование**.

### Области памяти

В JVM есть три главные области, куда попадают данные:

- **Stack (стек)** — здесь хранятся локальные переменные и **фреймы методов**. Для каждого потока свой стек. Фрейм создаётся при вызове метода и удаляется, когда метод завершается. Внутри фрейма параметры метода, локальные переменные и промежуточные значения.
- **Heap (куча)** — здесь живут **все объекты**, которые создаются через `new`. Это общая область для всех потоков.
- **Metaspace (метапространство)** — здесь хранятся метаданные классов: байт-код, описание полей и методов. Раньше эта область называлась PermGen, но в современных версиях Java её заменили на Metaspace.

### Сборщик мусора (Garbage Collector)

**GC** — это механизм, который автоматически удаляет из heap объекты, на которые больше никто не ссылается. Работает он не мгновенно: JVM сама решает, когда запустить сборку. В маленьких программах, как наша, GC, скорее всего, вообще не сработает, т.к. объектов слишком мало, память не забивается. Но важно понимать: как только объект становится недостижимым (на него нет ссылок ни из стека, ни из других живых объектов), он становится **кандидатом на удаление**.

## Разбор кода по строкам

### Подготовка (до выполнения main)

Прежде чем начнёт выполняться метод `main`, JVM делает следующее:

- Запускается сама JVM, создаётся Bootstrap ClassLoader.
- ClassLoader'ы по цепочке загружают класс `JvmComprehension` в **Metaspace**. Там появляется его описание: методы, поля, байт-код.
- JVM создаёт главный поток (`main thread`).
- Для этого потока выделяется **стек**.
- В heap создаётся массив `String[] args` (пустой, так как мы не передаём аргументы).

### Строка 1. int i = 1;

В **стеке**, в текущем фрейме метода `main`, создаётся локальная переменная `i` типа `int`. Ей присваивается значение `1`.

Так как `int` — это примитив (не объект), в heap ничего не создаётся. Всё хранится прямо в стеке.

### Строка 2. Object o = new Object();

Здесь появляется первый объект.

- Класс `Object` уже загружен Bootstrap ClassLoader'ом в Metaspace (он загружается ещё при старте JVM).
- В **heap** выделяется память под новый объект `Object`.
- В **стеке**, в фрейме `main`, создаётся переменная `o` типа `Object`. В ней хранится **ссылка** (адрес) на объект в heap. Сам объект в стеке не лежит, там только ссылка.

### Строка 3. Integer ii = 2;

Тут интересный момент — **autoboxing**.

- `2` — это примитив `int`, но переменная `ii` имеет тип `Integer` (это класс-обёртка).
- Java автоматически «заворачивает» число `2` в объект `Integer`. Это и называется autoboxing.
- Есть одна тонкость: для значений от **-128 до 127** Java использует **кэш** (`IntegerCache`). То есть объект `Integer(2)` не создаётся заново, он берётся из уже существующего кэша, который живёт в heap с момента загрузки класса `Integer`.
- В **стеке** создаётся переменная `ii`, и в неё записывается ссылка на этот объект из heap.

### Строка 4. printAll(o, i, ii);

Вызывается метод `printAll`, и тут начинается самое интересное:

- В **стеке** создаётся **новый фрейм** для метода `printAll`.
- В этот фрейм копируются **значения параметров**:
  - `o` — копируется ссылка на объект `Object` в heap (не сам объект, а именно ссылка).
  - `i` — копируется значение `1` (примитив копируется целиком).
  - `ii` — копируется ссылка на объект `Integer(2)` из heap.
- Управление передаётся в метод `printAll`.

### Строка 5. Integer uselessVar = 700;

- Внутри метода `printAll` в его фрейме создаётся локальная переменная `uselessVar`.
- Число `700` **выходит за пределы кэша** `IntegerCache` (-128…127), поэтому создаётся **новый объект** `Integer(700)` в heap.
- В переменной `uselessVar` в стеке хранится ссылка на этот объект.
- **Важно:** эта переменная больше нигде не используется. После завершения метода `printAll` ссылка на неё пропадёт, и объект `Integer(700)` станет **кандидатом на удаление сборщиком мусора**. Именно поэтому переменную назвали `uselessVar`, она, по сути, бесполезна.

### Строка 6. System.out.println(o.toString() + i + ii);

- Сначала вызывается `o.toString()`. Метод `Object.toString()` возвращает строку вида `java.lang.Object@1b6d3586`. В heap создаётся объект `String`.
- Затем идёт конкатенация: `String + int + Integer`. Каждое сложение создаёт **новую строку** в heap (компилятор может использовать `StringBuilder`, но результат всё равно новый объект).
- Числа `i` и `ii` автоматически приводятся к строке.
- Итоговая строка передаётся в `System.out.println()`, который выводит её в консоль.
- Все промежуточные строки после вывода становятся **кандидатами на удаление GC**.

### Возврат из printAll в main

- Фрейм метода `printAll` **удаляется** из стека.
- Локальные переменные `o`, `i`, `ii`, `uselessVar` перестают существовать.
- Объект `Integer(700)` в heap становится недостижимым → **кандидат на GC**.
- Управление возвращается в метод `main`.

### Строка 7. System.out.println("finished");

- Строковый литерал `"finished"` уже находится в **String Pool** (это часть heap). Он создаётся один раз при первом использовании и потом переиспользуется.
- `System.out` — это статическое поле класса `System`, который был загружен Bootstrap ClassLoader'ом ещё при старте.
- Строка выводится в консоль.
- Метод `main` завершается → его фрейм удаляется из стека.

### После завершения main

- Главный поток завершается.
- Все объекты, на которые больше нет ссылок (`Integer(700)`, промежуточные строки), становятся мусором.
- GC может их удалить, но **не обязательно прямо сейчас**. Это важно: GC недетерминирован, JVM сама решает, когда запускать сборку.
- Когда JVM завершает работу, вся память (heap, stack, metaspace) освобождается операционной системой.

## Про сборщик мусора — отдельно

В этом маленьком примере GC, скорее всего, **не сработает ни разу**: объектов слишком мало, heap не забивается. Но важно понимать принципы:

- **Что считается мусором:** объекты, на которые больше нет ссылок ни из стека, ни из других живых объектов, ни из статических полей.
- **Когда GC запускается:** по решению JVM: при заполнении heap, по таймеру или по явному вызову `System.gc()` (но так делать не рекомендуется).
- **Что делает GC:** находит недостижимые объекты и освобождает память. Может также уплотнять heap (compaction), чтобы не было «дырок».
- **Что не удаляется:** объекты, на которые есть ссылки. А также классы в Metaspace: они удаляются только при выгрузке класса, а это редкость.

## Итог

В этой программе:

- **Metaspace** хранит описание класса `JvmComprehension` и других загруженных классов.
- **Stack** хранит фреймы `main` и `printAll`, а в них локальные переменные (`i`, `o`, `ii`, `uselessVar`).
- **Heap** хранит объекты: `Object`, `Integer(2)` из кэша, `Integer(700)`, промежуточные строки, строку `"finished"` в String Pool.
- **GC** в такой маленькой программе, скорее всего, не запустится, но потенциально он бы удалил `Integer(700)` и промежуточные строки после завершения методов.

Вот и всё — JVM сама управляет памятью, а программисту не нужно вручную следить за освобождением объектов.
